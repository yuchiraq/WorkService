# Переход на SQLite

## Что подготовлено

По умолчанию остаётся JSON. Режим SQLite включается только переменной окружения;
самостоятельно сайт ничего не импортирует и не переключает.

Это **первый, совместимый этап миграции**: таблица `documents` содержит отдельный
JSON-документ для каждого раздела, с версией записи. Существующие модели и кеши
в памяти сохранены. Запись одного раздела атомарна, импорт всех разделов идёт
одной транзакцией. Включены WAL, `synchronous=FULL`, ожидание блокировки 5 секунд,
проверка версии схемы и блокировка второго процесса сервиса.

Это ещё не нормализованная реляционная схема. SQL-фильтрация, внешние ключи между
пользователями/назначениями/объектами и общие транзакции между разделами пока
не реализованы. Как и раньше, операции в нескольких разделах не являются одной
транзакцией. Для следующего этапа потребуются SQL-репозитории и таблицы связей.
Первый этап делает перенос обратимым, не совмещая его с переписыванием бизнес-логики.

Поддерживается **один процесс сервиса на одном сервере**, локальный диск. Не
использовать сетевую папку/NFS, синхронизируемую облачную папку или несколько
реплик сервиса. Не изменять базу внешними программами во время работы сервиса:
данные остаются также в его памяти.

Драйвер `modernc.org/sqlite` не требует CGO или gcc; минимальная версия Go
осталась 1.23, рекомендуемый toolchain указан в `go.mod`.

## Какие данные переносятся

- Пользователи, хеши паролей и настройки меню.
- Работники, включая уволенных; объекты; назначения и периоды отсутствия.
- Транспорт, записи и полная история привязок владельцев.
- Инвентарь, справочник наименований, остатки, версии и история изменений.
- Предложения и ошибки, настройки интеграций, контакты Telegram.
- Метаданные фото объектов: автор, подпись, дата, размеры, контрольная сумма.

Идентификаторы, числовые значения и исходные JSON-документы при импорте
сохраняются побайтно. `verify` сравнивает все документы, а не только количество
записей. Проверка структуры выявляет повреждённый JSON, повторяющиеся ID,
повторяющиеся логины, отсутствие администратора и потерянные фото. Ссылки
исторических записей на удалённые сущности выводятся как предупреждения:
они не удаляются автоматически.

Фотографии остаются **на диске**, а не в BLOB-полях SQLite. Путь по умолчанию:
`storage/object_photos`. При необходимости задайте абсолютный путь
`WORKSERVICE_PHOTO_DIR`; каталог должен быть доступен на запись пользователю
сервиса и не должен раздаваться nginx как публичная статика.

Сессии авторизации находятся в памяти процесса, поэтому после остановки
сервера потребуется повторный вход. `security.log` остаётся отдельным журналом.
Внешняя галерея другого сайта не переносится: сохраняется только её настройка
пути. Саму внешнюю папку и журнал при необходимости архивируйте отдельно.

## Перед переносом

1. Соберите новую версию и проверьте её на копии данных.
2. Остановите сервис, включая старые экземпляры и фоновые процессы. Старые
   версии не знают о новой блокировке каталога.
3. Сделайте отдельную копию всего `storage` и каталога `WORKSERVICE_PHOTO_DIR`,
   если он вынесен наружу. Храните копию вне рабочего диска сервера.
4. Выполняйте команды из корня проекта. Не запускайте сайт между `import` и
   `verify`: обычный вход уже изменяет дату последнего входа пользователя.

## Linux

```bash
CGO_ENABLED=0 go build -o workservice ./cmd/server
CGO_ENABLED=0 go build -o workservice-storage ./cmd/storage

./workservice-storage check --source ./storage
./workservice-storage import --source ./storage --db ./storage/workservice.db
./workservice-storage verify --source ./storage --db ./storage/workservice.db

WORKSERVICE_STORAGE=sqlite \
WORKSERVICE_SQLITE_PATH=/absolute/path/WorkService/storage/workservice.db \
./workservice
```

Для systemd задайте `WorkingDirectory` на каталог проекта и добавьте эти
переменные через `Environment=`. Не оставляйте второй старый процесс на другом
порту с теми же данными.

## PowerShell

```powershell
$env:CGO_ENABLED='0'
go build -o workservice.exe ./cmd/server
go build -o workservice-storage.exe ./cmd/storage

.\workservice-storage.exe check --source .\storage
.\workservice-storage.exe import --source .\storage --db .\storage\workservice.db
.\workservice-storage.exe verify --source .\storage --db .\storage\workservice.db

$env:WORKSERVICE_STORAGE='sqlite'
$env:WORKSERVICE_SQLITE_PATH='C:\tmp\WorkService\storage\workservice.db'
.\workservice.exe
```

Если фото находятся в другом каталоге, укажите `--photos /absolute/photo/path`
для каждой команды, а при запуске сервиса используйте тот же путь в
`WORKSERVICE_PHOTO_DIR`. Команды миграции используют явные флаги, а не эту
переменную окружения.

`check` не меняет JSON или фото и не создаёт SQLite. Команды создают служебный
файл блокировки каталога. `import` разрешён только в **новый файл базы**:
существующий файл, даже пустой, не перезаписывается. После прерванной попытки
проверяйте ошибку и выбирайте новый путь. Повторный запуск не объединяет базы.

После переключения изменения записываются только в SQLite; старые JSON
не синхронизируются и остаются исходной точкой отката.

## Резервная копия и откат

Кнопка в настройках сохраняет согласованный снимок записанных документов и
все связанные фото в новый каталог `storage/backups/<дата>`. Формат копии
одинаков для JSON и SQLite: JSON-документы, `object_photos/` и файл
`backup-manifest.json` с SHA-256 файлов. Прерванная копия не публикуется как
готовая. Копия содержит персональные данные, хеши паролей и токен Telegram;
не добавляйте её в Git и не отдавайте через HTTP.

Не копируйте только открытый `.db` без WAL. Для актуального обратного экспорта
остановите сервис и выполните:

```bash
./workservice-storage export --source ./storage --db ./storage/workservice.db \
  --out ./rollback-storage
./workservice-storage check --source ./rollback-storage
```

Добавьте `--photos`, если используется нестандартный каталог. Экспорт включает
все связанные фото в `rollback-storage/object_photos`. Каталог назначения
должен быть новым; существующий каталог не перезаписывается.

Сохраните нынешний `storage` под другим именем, поставьте экспортированный
каталог на место `storage`, переключите `WORKSERVICE_STORAGE=json` и уберите
`WORKSERVICE_PHOTO_DIR`, чтобы использовать фото из восстановленной копии
(либо отдельно восстановите внешний каталог). Запустите сервис и проверьте
вход, назначения, транспорт, инвентарь и фото. Использовать старые JSON без
свежего экспорта можно только если после перехода в SQLite ещё не было изменений.

## Фото объектов

Доступ есть у администраторов, ответственного и действующих работников,
имеющих назначения на объект, включая исторические назначения. Смотреть и
добавлять могут все с таким доступом; менять подпись и удалять могут автор,
ответственный и администратор. Прямые ссылки на изображения тоже проверяют
авторизацию и доступ к объекту. Уволенные работники доступа не имеют.

Принимаются JPEG, PNG и WebP до 24 МБ и 50 Мп. HEIC пока не поддерживается.
Изображения преобразуются в JPEG с качеством 88 и размером до 2560 пикселей
по длинной стороне; для списка создаётся миниатюра до 480 пикселей. Поворот EXIF
учитывается, GPS и остальные метаданные удаляются. **Оригиналы не сохраняются**:
для исполнительной документации, где важен исходник, храните его отдельно.
Повторный снимок после оптимизации не дублируется внутри одного объекта.
Лимит объекта: 500 фото / 2 ГБ основных изображений, миниатюры занимают
дополнительное место. За раз можно выбрать до 30 файлов, они грузятся по одному.

При удалении объекта с фото операция отклоняется: удалите фото отдельно или
переведите объект в оконченные. При обрыве удаления после сохранения метаданных
может остаться неиспользуемый файл; в фототеке он не появится. Не удаляйте
файлы из каталога вручную, пока они есть в метаданных.

## Проверки разработчика

```bash
go test ./...
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o /tmp/workservice ./cmd/server
```

Интеграционные тесты запускают одинаковые сценарии сервиса на обоих бэкендах,
включая права доступа к фото, CSRF, конфликт версий, резервную копию, инвентарь,
назначения и историю транспорта. Отдельно проверяются повторное открытие БД,
отказ второго процесса, откат неуспешного импорта и побайтный обратный экспорт.

Справка: [SQLite WAL](https://www.sqlite.org/wal.html),
[драйвер modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite),
[обработка ориентации imaging](https://pkg.go.dev/github.com/disintegration/imaging#AutoOrientation).
